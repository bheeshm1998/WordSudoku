# Feature Ideas

## 1. Expand Board Size to 9x9
- **What**: Increase the grid from the current 5x5 to a 9x9 board (same as traditional Sudoku).
- **Why**: A larger board significantly increases complexity and challenge, making the game more engaging for experienced players.
- **Impact**: Requires updating `BOARD_SIZE` in constants.ts, extending the `GRADIENT` color map to handle 9 positions per direction (leftToRight_0..8, etc.), and optimizing validation to use a `Set<string>` for `ALL_WORDS` instead of a linear scan — the current O(n² × substr²) approach will be too slow at 9x9.

## 2. Dynamic Board Initialization for Any Size
- **What**: The board should automatically initialize correctly for any `BOARD_SIZE` (e.g., 4x4, 5x5, 9x9), not just 5x5.
- **Why**: Currently, logic may break if BOARD_SIZE changes. Making initialization size-agnostic enables the 9x9 board and future flexibility.
- **Impact**: `fillTheBoardWithAWord` and `getAListOfRandomIndicesDistributedUniformly` must work across all sizes. `NUM_OF_PREFILLED_CELLS` should also scale with board size.

## 3. Add Undo Functionality
- **What**: Allow the player to undo their last input (or multiple steps of inputs).
- **Why**: Mistakes happen; an undo button lets players recover without restarting the entire game, improving the user experience.
- **Impact**: Requires maintaining a history stack of cell changes. Each undo pops from the stack and restores the previous letter.

## 4. Diagonal Word Validation
- **What**: In addition to checking rows and columns for valid English words, also check both diagonals (top-left to bottom-right and top-right to bottom-left).
- **Why**: Currently diagonals are not validated, so a player could form a word along a diagonal and it would not be flagged as a violation. Adding diagonal checks makes the game rules consistent across all directions.
- **Impact**: Add diagonal traversal logic in `checkIfTheBoardIsSolved`. Contiguous substrings of length ≥3 along both diagonals must be validated the same way rows and columns are.

## 5. Keyboard Navigation Between Cells
- **What**: Allow players to navigate through the grid using arrow keys (or WASD) instead of only clicking.
- **Why**: Keyboard navigation speeds up input for experienced players, making the game feel more fluid and professional — similar to how spreadsheets or Sudoku apps work.
- **Impact**: Track a "focused" cell separate from the "active" cell. Arrow keys / WASD move focus; Enter or typing focuses the selected cell and accepts input.

## 6. Increase Prefilled Cells for Better Starting Points
- **What**: Start with more pre-filled (locked) cells so players have a clearer path to solving.
- **Why**: Currently `NUM_OF_PREFILLED_CELLS = 10` on a 5x5 board (40% filled). Increasing this number gives players more clues and reduces ambiguity, making the game more approachable.
- **Impact**: Adjust `NUM_OF_PREFILLED_CELLS` in constants.ts. The `fillTheBoardWithAWord` method must ensure pre-filled letters still respect the no-duplicate-in-row/column constraint.

## 7. Randomize Initial Letters
- **What**: Instead of always using `INITIALIZING_WORD = "AETIONSUEI"` as the source of pre-filled letters, select random letters from the entire alphabet or from the word list itself.
- **Why**: Current fixed initialization word limits variety. Randomizing starting letters means each new game is different, improving replayability.
- **Impact**: Replace `shuffleString(INITIALIZING_WORD)` with a method that picks random letters (ensuring no row/column duplicates). Also update the pre-fill logic to work from a broader pool.

## 8. Robust Scoring System (Time + Moves + Accuracy)
- **What**: Score = base score out of 1000, adjusted by time taken, number of moves, incorrect moves, and the number of times validation failed during play.
- **Why**: Currently scoring is purely time-based. A multi-factor scoring system rewards not just speed but also accuracy and efficiency, making competition more meaningful.
- **Impact**: Track moves count, failed validation attempts, and incorrect input counts. On completion, compute: `score = min(1000, basePoints - timePenalty - movePenalty - errorPenalty)`. Store best score as a number rather than a time string.

## 9. Mobile Responsiveness
- **What**: Ensure the game is fully usable on mobile devices — cells must be large enough to tap, the layout must adapt to small screens, and input must work via the on-screen keyboard.
- **Why**: A significant portion of users will access the game from phones. If it is not mobile-friendly, they will have a poor experience or not use it at all.
- **Impact**: Use CSS media queries or flex/grid layouts that adapt cell size to viewport. Ensure the input field receives focus properly on mobile and does not trigger unwanted zoom.

## 10. Handle Missing Word Meanings Gracefully
- **What**: When a player asks to "see meaning" of a word, the app currently shows an alert if no definition is found. Instead, show an inline message on the modal: "No definition found for [word]."
- **Why**: Current behavior (alert + dismiss) is abrupt and disruptive. Graceful handling keeps the player in flow and does not interrupt their game.
- **Impact**: In `getWordMeaning`, instead of showing an alert on error, set an error message state that the modal component displays. Also consider removing words with no dictionary entry from `final_words.txt` during regeneration to reduce these cases.

## 11. Display Game Rules on Screen
- **What**: Show a concise set of game rules at the top of the screen (or in a collapsible help section).
- **Why**: New players may not know the rules (no repeated letters, no words of 3+ letters in any direction). Displaying rules removes guesswork and reduces friction for new users.
- **Impact**: Add a small rules panel above or beside the board. Keep it brief: "Fill all cells. No repeated letters in any row/column. No valid English words of 3+ letters in any direction (rows, columns, or diagonals)."

## 12. Fix Double-Click Bug on Cells
- **What**: When a cell is clicked twice in a row, the second click does not trigger a change event, and letters may appear in lowercase instead of uppercase.
- **Why**: This is a bug that breaks the expected behavior — clicking a cell should always activate it and allow input. It also causes case inconsistency (letters appearing as lowercase).
- **Impact**: In `cell.component.ts`, the `onClickInput` method calls `setSelectionRange` but does not re-trigger the focus. When clicking the same active cell twice, the input's selection range may not update correctly. Ensure `cellInput.nativeElement.focus()` is called to reset the input state on every click.

## 13. Lock Board After Solving
- **What**: Once the player completes the board successfully, lock all cells (no further edits) until they explicitly click "Restart."
- **Why**: Currently the board stays interactive after solving, which risks accidental changes. Locking reinforces the "puzzle solved" state and clearly separates completion from continued play.
- **Impact**: The `disableUserAction` flag already exists and is set on success. Ensure all input handlers in `cell.component.ts` and `board.component.ts` respect this flag and reject changes when it is true.

## 14. Differentiate Locked (Prefilled) Cells Visually
- **What**: The locked cells already have `BLOCKED_CELL` color (#618264), but make the styling more prominent — for example, a different border, a subtle icon, or bolder text — to clearly communicate that these cells cannot be edited.
- **Why**: Players may accidentally try to edit a locked cell and be confused when nothing happens. Clearer visual distinction eliminates this friction.
- **Impact**: Update the cell component's SCSS to add a border, shadow, or icon for locked cells. The current `CELL_COLOR.BLOCKED_CELL` background is sufficient for color but could be complemented with a visual marker.

## 15. Complete `makeAnArrayOfGoodPositions` Method
- **What**: Implement the `makeAnArrayOfGoodPositions` method referenced in the code (currently only mentioned in idea.txt, not implemented).
- **Why**: This method is presumably intended to determine strategic positions for pre-filled cells — for example, positions that ensure the board has a unique solution or that spread clues evenly across the board.
- **Impact**: Design and implement the method in `utility-methods.ts`. It should return an array of cell indices that are good candidates for pre-filling, based on board size and desired cell count.
